# 工作流（当前计划）

## 1. 目标
- 保持当前 `/recommend` 行为稳定。
- 以最小风险新增流式输出能力。
- 引入 0.6B 小模型提升分流质量，同时保留规则稳定性。
- 通过 rerank 提升检索结果质量。

## 2. 已确认的设计决策

### 2.1 `@task` 使用范围
- `@task` **不是**给所有 node 函数统一加的。
- 当前是 StateGraph 结构，node 函数返回 `dict`。
- 推荐做法：把外部高耗时调用（LLM/搜索/网络/IO）抽成 `@task` 单元。
- 现有 `@task` 位置：
  - `nodes.py:596`
  - `nodes.py:741`

### 2.2 检索 rerank（当前实现）

- 开关：`RETRIEVAL_ENABLE_RERANK`（默认 `false`，开启后生效）。
- 子问题数量：默认 `2~3`（`SUB_QUESTION_MIN_COUNT=2`、`SUB_QUESTION_MAX_COUNT=3`）。
- 子问题检索：`retrieve(query=subq, top_k=settings.TOP_K)`，当前 `TOP_K=4`。
- Web 召回上限：`TAVILY_MAX_RESULTS=2`。

当前是“两段式 rerank”：

1. 子问题级（`retriever.py::retrieve`）
   - 召回：向量检索 + Tavily 合并。
   - 去格式化：统一为 `Document`，补齐 `metadata.doc_id/retrieval_source/score`。
   - 若开关开启：调用 `rerank_documents(query=subq, docs=merged_docs, top_n=4)`，按分数降序返回。
   - 当前 `rerank_documents` 优先走 `cross_encoder_hybrid`：使用 `BAAI/bge-reranker-base` 产出 `cross_encoder score`，再与线性特征分融合，当前公式是 `0.8 * cross_encoder + 0.2 * linear_score`。
   - 线性部分不是只看 3 个特征，而是综合 `retrieval / overlap / source / freshness / skill / memory`，权重可配置。
   - 若 Cross-Encoder 加载失败、预测失败或被显式关闭，则自动回退到纯线性 rerank，并回写 `doc.score` 与 `metadata.score`。

2. 全局级（`nodes.py::retrieve_node`）
   - 收集：遍历每个 `sub_question` 调 `retrieve(...)`，累积到 `all_docs`；`retrieval_records` 仍按子问题记录。
   - 去重：按 `doc_id` 去重（优先 `metadata.doc_id`，为空回退 `_extract_doc_id(..., "merged", idx)`）。
   - 全局查询：优先 `state.user_query`，为空才回退为拼接子问题文本。
   - 全局重排：`rerank_documents(query=global_query, docs=unique_docs, top_n=3)`。
   - 截断：`MAX_EVIDENCE=3`，取 `final_docs = ranked_docs[:3]`。
   - 写回：`evidence` 只写 1 个聚合项，`documents/search_results/retrieved_doc_ids` 都只保留这 3 条，保证最终 LLM 最多看到 3 个 chunk。

补充：
- `coverage_check_node` 已适配单聚合 evidence：当 `evidence` 只有 1 条且对应 `user_query` 时，若 `documents` 非空则按“已覆盖全部子问题”处理，避免误触发继续迭代。

当前 pipeline：
- question
- subq generation (2~3)
- retrieve per subq (top4, tavily<=2)
- merge all docs
- dedup by doc_id
- global rerank
- top3 evidence (single aggregated item)
- LLM answer

90 秒口语整合版（可直接对面试官说）：
我这块 rerank 的设计，核心思路是先把“能召回的都召回上来”，再在进入大模型之前做一次更强的相关性筛选。当前实现其实是一个两段式 rerank。第一段发生在子问题级，因为一个用户问题会先被拆成 2 到 3 个 sub-question。每个 sub-question 会先做检索，当前是向量召回加少量 web 召回，拿到候选之后先统一成同一种 `Document` 结构，补齐 `doc_id`、`retrieval_source`、`score` 这些字段。如果开关 `RETRIEVAL_ENABLE_RERANK` 打开，就先对这一批候选做一次子问题级 rerank。当前实现不是纯线性分，而是优先用 `BAAI/bge-reranker-base` 做 Cross-Encoder 打分，再和线性特征分做一个 hybrid 融合；只有在模型加载失败或者关闭的时候，才回退到纯线性 rerank。

第二段发生在全局级。也就是所有 sub-question 的结果汇总之后，我不会直接喂给大模型，而是先按 `doc_id` 去重，再用原始用户问题做一次全局 rerank，最后只保留 top3 作为最终 evidence。这样做的原因是，子问题级 rerank 解决的是“单个子问题下谁更相关”，全局级 rerank 解决的是“站在整个用户问题视角，哪些证据最值得进入最终回答”。所以最后大模型实际看到的证据上限是 3 个 chunk，这样能控制噪音和上下文长度。

另外在 Workflow 里我还规划了后续优化路线，不是“第二阶段才上 bge”，而是基于当前已经存在的 cross-encoder hybrid，继续把召回池做宽，比如从更大的向量候选集里做强重排，形态上更接近 `vector top20 -> rerank -> top3`。这样 trade-off 很明确：相关性有机会继续提升，但延迟也会涨，所以我会重点看 `retrieval_recall`、`answer_correctness`、`latency p50/p95` 和 fallback rate，确保收益是真的，不是单纯把系统变慢了。

#### 2.2.1 后续优化方向（宽召回 + 强重排）：`vector top20 -> rerank -> top3`

适用目标：
- 当前代码已经优先采用 `BAAI/bge-reranker-base` 作为 Cross-Encoder reranker，并在失败时回退到线性 rerank。
- 后续这条方案的重点，不是“第一次引入 bge”，而是把候选池做宽，再让当前 rerank 机制在更大的候选集上发挥作用。

建议改法（落地顺序）：
1. `config.py` 新增参数：
   - `RETRIEVAL_VECTOR_TOP_K=20`
   - `RETRIEVAL_FINAL_TOP_N=3`
   - `RETRIEVAL_RERANK_BACKEND=cross_encoder`（默认且固定）
   - `RETRIEVAL_CE_MODEL=BAAI/bge-reranker-base`
   - `RETRIEVAL_CE_BATCH_SIZE=16`
2. `retriever.py` 新增 Cross-Encoder 载入与打分函数（建议懒加载单例），接口建议：
   - `cross_encoder_rerank(query: str, docs: List[Document], top_n: int) -> List[Document]`
3. `retrieve()` 调整为“宽召回 + 强重排”：
   - 向量召回：`similarity_search(query, k=RETRIEVAL_VECTOR_TOP_K)`（top20）
   - Web 召回：保留低权重（`TAVILY_MAX_RESULTS=2`）
   - 合并后先按 `doc_id` 去重，再走当前的 rerank 机制重排（优先 Cross-Encoder hybrid，失败时回退 linear）
   - 只返回 `top3`
4. `nodes.py::retrieve_node` 继续做全局合并与单聚合 evidence，保证最终 LLM 看到的证据上限仍是 3 条。
5. 保留 fallback：
   - Cross-Encoder 加载失败/超时/预测失败时，自动回退到现有线性分支，作为兜底。

推荐伪代码：

```python
# retriever.py
vector_docs = similarity_search(query=query, k=settings.RETRIEVAL_VECTOR_TOP_K)  # 20
web_docs = _tavily_search(query=query)  # <=2
merged_docs = dedup_by_doc_id(_normalize_documents(vector_docs, "vector") + _normalize_documents(web_docs, "web"))

ranked_docs = rerank_documents(query=query, docs=merged_docs, top_n=settings.RETRIEVAL_FINAL_TOP_N)  # 3
# 内部优先 cross_encoder_hybrid，失败时回退 linear

return ranked_docs
```

升级后 pipeline（推荐形态）：
- vector search top20
- rerank（优先 `bge-reranker-base` cross-encoder hybrid，失败回退 linear）
- top3
- LLM answer

验收指标（与现状对比）：
- `retrieval_recall`（是否提升）
- `answer_correctness`（是否提升）
- p50/p95 latency（是否在可接受范围）
- 失败回退率（cross-encoder -> linear）

### 2.3 分流策略升级
- 当前分流基于规则/分词词表。
- 引入 0.6B 小模型做分流，但采用**混合分流**：
  - 先走硬规则
  - 再走模型判别
  - 低置信度回退到现有规则/默认策略
- 不建议一步到位“全量替换规则”。

## 3. 推荐改动顺序

### 阶段一：先稳质量（先于流式传输）
1. 保留现有规则分流作为基线。
2. 接入 0.6B 混合分流：
   - 输出严格 JSON：`mode`、`confidence`、`reason`
   - 低于阈值回退（建议阈值 `0.7`）。
3. 在检索链路接入 rerank（合并后、下游使用前）。
4. 仅对外部高耗时调用增加/调整 `@task`。

### 阶段二：安全接入流式输出
1. 先定义流式协议（先不改业务逻辑）：
   - 事件类型：`started`、`progress`、`awaiting_human_confirmation`、`final`、`error`、`done`
   - 通用字段：`session_id`、`event`、`timestamp`、`trace_id`
2. 新增 `/recommend/stream`（SSE 或 `StreamingResponse`），保留旧 `/recommend`。
3. 将执行路径改为可发出“阶段级”流事件。
4. 前端按会话消费流（每个会话独立连接与 loading 状态）。

### 阶段三：增强项
1. 可选：接入 LLM token 级流式输出。
2. 在确认瓶颈后，扩展 `@task` 覆盖面。
3. 在流式链路稳定后，再评估是否弱化/下线旧非流式接口。

## 4. 验收标准
- 混合分流上线后，分流误判率下降，或至少不高于当前规则版。
- rerank 上线后，候选结果相关性稳定提升（有离线/在线对比指标）。
- 新增 `/recommend/stream` 不影响现有 `/recommend`。
- `awaiting_human_confirmation` 能正确通过流式事件传递并被前端消费。
- 会话切换时不出现 loading/流状态串话。
